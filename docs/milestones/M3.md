# Milestone M3 — Planning agent (task list)

**Status:** ✅ complete (v0.3.0)

**Demo:** a multi-step goal such as _"Compare the populations of France and
Germany"_ produces a **plan checklist** that renders, then ticks each task
`pending → running → done` live as the agent works, and finishes with a
**synthesized** answer composed across the task outputs. Persisted and replayable
exactly like M1/M2.

> With the `echo` provider (no Ollama) the planner returns a single task equal to
> the goal, the executor answers it directly, and synthesis short-circuits — so a
> full plan → execute → answer cycle still completes model-free. The multi-task
> plan → execute → synthesize flow is exercised deterministically by the FakeLLM
> tests. With Ollama the real planner produces a multi-task list.

Full design rationale: [RFC-0001](../rfc/0001-m3-planning-agent.md).

## 1. Objectives

1. **Planner** — one LLM call turns a goal into an ordered list of ≤5 tasks
   (`{description, success_criteria, suggested_tool}`), tolerant-parsed with a
   bounded repair loop; output defensively normalized (drop empties, null unknown
   tools, hard-cap, fall back to a single task) (design §1.1).
2. **`tasks` table** — the 3rd V2 table; ordered per-run task rows with an FSM
   (`PENDING → RUNNING → DONE|FAILED`).
3. **Context Builder** — assembles each task's executor prompt from the goal,
   task, and truncated prior-task outputs (design §1.11). The executor becomes
   **execution-only** and receives prebuilt messages.
4. **Synthesizer** — a distinct LLM call composes the final answer from task
   outputs; single-task plans short-circuit ([ADR-0010](../adr/0010-synthesis-as-distinct-call.md)).
5. **PLANNING run state** activated; executor `thought`/`tool.*` events tagged
   with `task_id`; new `plan.created` / `task.started` / `task.completed` /
   `task.failed` events.
6. **Plan checklist UI**, event-sourced ([ADR-0009](../adr/0009-event-sourced-plan-checklist.md)),
   with `GET /runs/{id}/tasks` as a projection.
7. **Cancellation** works during planning and between tasks.

## 4. Design decisions

- **Flat plan, hard-capped.** `{"tasks":[…]}`, ≤5, with two few-shot tight-plan
  examples and an explicit no-filler instruction to fight 7B over-production
  (design §1.1). Normalization is defensive: unknown `suggested_tool` hints are
  nulled against the registry, empty descriptions dropped, and an empty plan falls
  back to a single task equal to the goal (the runtime never sees an empty plan).
- **Invalid plan fails cleanly.** Repair ≤2, then `PlannerError` → run `FAILED`
  during `PLANNING` — never a crash (design §1.1, success criterion 4).
- **Typed `TaskContext`** is the stable seam between planning and execution
  (RFC-0001 addendum): the runtime builds it, the Context Builder consumes it.
  Later milestones (memory recall, replanning, multi-agent) extend it additively
  rather than reworking the executor's input each time.
- **Executor is execution-only** (RFC-0001 decision 4): it takes prebuilt
  messages and never constructs context — so its signature changed from
  `run(run_id, goal, cancel)` to `run(run_id, messages, cancel, *, task_id)`.
- **Synthesis is a distinct call** ([ADR-0010](../adr/0010-synthesis-as-distinct-call.md)),
  short-circuited for single-task plans.
- **Checklist is event-sourced** ([ADR-0009](../adr/0009-event-sourced-plan-checklist.md));
  `GET /runs/{id}/tasks` is a projection.
- **Task failure fails the whole run in M3** (partial plan + outputs preserved in
  the ledger). Retry/replan/graceful-abort is the entire point of **M4** — keeping
  it out preserves the milestone boundary.
- **`jsonio` is shared** — the tolerant JSON extraction factored out of
  `envelope.py` is reused by the planner (one parser, two callers).

## 5. Acceptance tests (`make test-m3`)

- `test_planner.py` — valid plan; clamp >5 → 5; drop empty descriptions; null
  unknown tool; repair-then-succeed; invalid-after-repair → `PlannerError`;
  0-task fallback.
- `test_context.py` — includes description + success_criteria + tools; includes
  prior outputs + plan position; truncates long outputs; single-task omits plan
  position.
- `test_synthesizer.py` — combines multiple outputs; single-task short-circuit
  (no LLM call); forced synthesis; empty outputs.
- `test_runtime_m3.py` — multi-task plan executes in order and synthesizes;
  single-task short-circuit; invalid plan → run FAILED; task failure →
  `task.failed` + run FAILED; cancel during planning; cancel between tasks.
  Asserts ordered lifecycle, per-task `task_id` tagging, monotonic `seq`.
- `test_persistence.py` — `tasks` bulk-create + ordered read, status transitions,
  cascade delete with the run.
- M1/M2 tests remain green (**86 tests total**).

## 6. Not in scope (later milestones)

Reflection / retry / replan / graceful abort (M4); episodic memory + recall at
plan time + eval harness (M5); crash-resume, `code_sandbox`, `PAUSED` (M6). The
`SKIPPED` task state is declared but first exercised in M4 (when a replan drops
remaining tasks).
